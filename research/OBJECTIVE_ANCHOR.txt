Scope

Evidence from disassembly
- Mission HUD construction at RVA 0x12E96D0 includes the known Player Status
  panel (+0x60), stamina (+0x5778), squad (+0x1F8C8), and other panels.
- RVA 0x12E9DFE passes mission HUD +0x46050 to constructor 0x17CE750.
- 0x17CE790..0x17CE7D9 sets size (300,430) and both anchor/pivot pairs to
  (1,1): this is a right/top anchored container, not a bottom-right panel.
- Child groups at +0x610 and +0x5848 are controlled separately by
  0x17D03A0. Their visibility flags are stored at +0xFE220/+0xFE221.
  That update reads two HUD-option-like settings and a HUD held-state flag,
  fades these groups, then adjusts +0x330/+0x4B8 geometry using their sizes.
- Child region +0x6DF0 has up to 16 detail rows, stride 0xF068; update code
  0x17CF8A0 selects content from mission-like instances before calling
  0x184B700. This supports the objective-panel hypothesis but does not prove
  which visible group is primary/secondary or its final on-screen bounds.
- Strings hud_primary_objective / hud_secondary_objective are referenced
  by settings code at 0x102FD67 / 0x102FD8D. These are settings identifiers,
  not direct evidence of the panel address; do not confuse the two.

Why automatic following is not enabled yet
The constructor's 300x430 is a container size, not necessarily the occupied
visible region. Collapsed content, secondary tasks, fades, native HUD scale,
localization/wrapped lines, and held-map state can change the actual bottom.
Using the fixed container bottom would create unexplained gaps or overlap.
Reading the existing widget screen x/y/size/scale/shown fields should be
possible, but correspondence and occupied bounds require live validation.
